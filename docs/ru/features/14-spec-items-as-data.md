# Feature 14: пункты ТЗ как данные — ТЗ ратифицирует человек, агент не подтверждает его сам

> Русский · [English](../../features/14-spec-items-as-data.md)

> **Статус:** Реализовано (этапы 1–6: модель данных, CLI, инбокс в десктоп-приложении, MCP-доступ, напоминания; подтверждение пунктов человеком идёт) · **Обновлено:** 2026-10-24
> **Суть:** требования фичи живут как машиночитаемые пункты в секции `## ТЗ` фича-доки:
> ID (`R1..RN`, не переиспользуются), дословная цитата-источник (пересказ помечен
> «выведено агентом») и связи-теги на задачи. Агент выполняет работу и ставит
> «сделано» — с обязательным доказательством; **подтверждение пункта — жест
> человека**, через тот же инбокс верификации, что у задач
> ([фича 11](./11-task-tags-and-verification.md), [фича 13](./13-ui-only-verification.md)).
> Три человеческие точки: верификация ТЗ до первой рабочей задачи → подтверждение
> пунктов по ходу → закрытие/переоткрытие.
> **Ключевые факты:**
> - Выросло из реального фейла (рассказан в [фиче 10](./10-code-intelligence-clean-room.md)):
>   расплывчатые требования → агент записал ТЗ «по минималке» и сам пометил выполнено →
>   «20% от референса и видения, хотя всё запускается».
> - Два статуса пункта: `агент: сделал` (ставит исполнитель, доказательство обязательно)
>   и `человек: <ступень> @актёр дата` (ставит только человек) — подтверждение «впрок»,
>   до всякой работы, разрешено и видно отдельно.
> - `devst feature close` отказывает, пока есть пункты вне {подтверждён, отклонён,
>   НЕ-цели}; неподтверждённые must блокируют закрытие, should/could становятся
>   задачами-переносами.
> - Удаление пунктов запрещено; смена смысла после ратификации возвращает пункт в цикл
>   кандидата. Строгость обязательна для всех новых фич; старые проходят ретроспективу.
> **Связанное:** [фича 11](./11-task-tags-and-verification.md) (ступени доверия переиспользованы дословно) ·
> [фича 13](./13-ui-only-verification.md) (ui-required: уровень пишет только десктоп-приложение) ·
> [фича 12](./12-activity-journal.md) (история статусов) ·
> [фича 05](./05-reminder-system.md) (напоминание «фича протухла с неподтверждёнными пунктами») ·
> [ADR-010](../decisions/adr-010-detect-dont-block.md) (мягкая блокировка) ·
> [ADR-020](../decisions/adr-020-tauri-sidecar.md) (мутации UI через сайдкар)

## Сценарии

1. **Верификация ТЗ (точка 1).** Автор говорит «хочу как у X» → агент раскладывает
   источник на пункты R1..RN с дословными цитатами или пометками «выведено агентом» →
   pending-запрос попадает в инбокс → автор правит формулировки (обычно через агента,
   вопросником) и подписывает «верифицировано». Только после этого открываются рабочие
   задачи фичи — мягко: напоминание и правило скилла, не жёсткий запрет.
2. **По ходу (точка 2).** Агент закрыл задачи пункта и поставил «сделано» с
   доказательством (коммит / тест / дока) → пункт попадает в инбокс (можно пачками) →
   человек открывает, видит цитату-источник и срез тулз, выбирает ступень →
   «Проверено» или «Сделано не то» (возврат в работу, агентская галка сбрасывается,
   событие записывается).
3. **Закрытие (точка 3).** `devst feature close 14` — отказ, пока есть пункты вне
   {подтверждён, отклонён, НЕ-цели}; неподтверждённые must блокируют, should/could
   предлагается превратить в задачи-переносы, привязанные к своим пунктам.
4. **Переоткрытие.** `devst feature reopen 14` с причиной → фиксируется сам факт;
   подтверждённые пункты сохраняют статус, отклонённые не воскресают (возврат — только
   новым пунктом-кандидатом), новые или изменённые пункты проходят цикл заново.
5. **Старт сессии агента.** Brief сессии и MCP-тулза `get_feature_items` показывают по
   каждой фиче, какие пункты верифицированы, какие ждут подтверждения, какие отклонены —
   агент работает ровно по этому срезу и никогда не пере-делывает подтверждённое.

## Модель данных

- Истина гибридная, как всюду в devst: формулировки и источник живут в фича-доке
  (markdown, ревьюится в git); статусы и связи — в базе реестра, аддитивная миграция
  с таблицей «пункт ↔ задача» многие-ко-многим («типо как теги», поздние фиксы включительно).
- Приоритеты пункта: must / should / could; must блокирует закрытие.
- `verifyMode` работает ровно как у задач: `open` пишет уровень напрямую, дефолтный
  `ui-required` только создаёт pending-запрос, который разрешает десктоп-приложение
  ([фича 13](./13-ui-only-verification.md)).
- Отклонённый пункт («сделано не то») возвращается в работу с комментом и событием
  в журнале; фичу можно переоткрыть с фиксацией факта.

## Что видит человек

В инбоксе пункты ТЗ стоят с бейджем «пункт ТЗ фичи» рядом с задачными запросами;
диалог подтверждения показывает формулировку, дословный источник, связанные задачи,
доказательства агента и срез тулз; человек выбирает одну из тех же ступеней доверия
(deep / smoke / skim / delegated / blind / manual — [фича 11](./11-task-tags-and-verification.md)).
Прогресс по фиче — верифицировано X/N, подтверждено Y/M — виден в доске и в
десктоп-приложении. Напоминание срабатывает, когда фича в работе сидит с
неподтверждёнными пунктами дольше N дней (дефолт 3). Проблемы формата секции (нет
секции ТЗ, must-пункт без источника) — предупреждения в `devst check`, никогда не ошибки.

## НЕ-цели

- Не линтуем содержание формулировок — только структуру секции.
- Не распространяем на одиночные задачи вне фич.
- Не заводим отдельную шкалу ступеней для пунктов — переиспользуем единую шкалу проекта.
- Не удаляем пункты (только «отклонён» или «перенесён в НЕ-цели», с причиной) и не правим
  историю статусов задним числом.
- Не блокируем работу жёстко до верификации ([ADR-010](../decisions/adr-010-detect-dont-block.md)).
