# Feature 06: kb: установщик практик-скиллов — большие практики, per-project, напоминатель

> Русский · [English](../../features/06-kb-practice-installer.md)

> **Статус:** дизайн (протокол собран; разработка не начата) · **Обновлено:** 2026-09-13

**Суть:** kb в devst — это НЕ «база текстов». Это **менеджер больших практик**:
папки-скиллы (SOLID, Clean Architecture, FSD, Micro-frontends, MVC, ts-idioms…),
которые devst устанавливает в харнесс как скиллы, включает/выключает per-project
конфигом, напоминает агенту в начале сессии («пишем по Clean Architecture») и
тычет «смотри скилл X!» при нарушениях. Плюс «линтинг без установленного
линтера»: малые машинные чеки (секреты/TODO/тесты), вшитые в те же паки.

**Ключевые факты:**

- Киллер-фича: текст + зубы — каждая практика = текст (чеклист/скилл) + опциональные машинные чеки, а не просто база текстов.
- Правило скорости: потолок 1 секунда на хуковый чек; чек, который не влезает, НИКОГДА не режется молча — агент приносит замеры и спрашивает автора «а точно ли норм будет?»; решает только автор.
- Общие практики = канон devst (вшиты бинарными ассетами, ADR-018); проектно-специфичные живут в проектных доках.
- На старте warn-only; severity каждого чека — данные, эскалация в strict через самодокументируемый per-project конфиг.
- 9 решений протокола, 7 этапов; первый образец пака — **ts-idioms** (Omit/Pick/satisfies/вывод типов вместо дублирования типов).

**Связанное:** [фича 04](./04-task-registry.md) (гейты/вердикты) · [фича 05](./05-reminder-system.md) (система напоминаний — носитель) · [ADR-018](../decisions/adr-018-sea-binary-distribution.md) (канон вшит ассетами) · задачи T-10 (зонтик) и T-17 (salvage внутренней методологии dev-standard) · концепция в architecture/01

## 1. Суть и потребители

| Потребитель | Как пользуется |
|---|---|
| Автор | «включи мне FSD и ts-idioms на этом проекте» — devst ставит скиллы, снимает лишние, напоминает в SessionStart |
| ИИ-агент | получает малые напоминания активных практик + полные тексты в своих скиллах; чеки ловят нарушения в момент правки |
| Чужая репа без линтеров | санитарный минимум (секреты/TODO/тесты) приезжает с бинарём; ничего устанавливать в проект не надо |

## 2. Сценарии

1. Настройка проекта: `devst kb install clean-architecture ts-idioms` → скиллы в
   харнессе, devst.json запоминает набор; `remove` — снимает ненужное.
2. Старт сессии: панель напоминаний несёт малую часть активных практик —
   «пишем по Clean Architecture» (one-liner, не текст).
3. Работа: агент плодит дублирующие типы там, где есть связь данных →
   напоминание «смотри скилл ts-idioms» (маппинг чек → скилл).
4. Правка кода без тестов: эвристика покрытия (сначала умный маппинг — №7).
5. Обновление: практики обновляются постоянно — апдейт паков через update-flow,
   свежесть как данные («Проверено» + TTL, провайдер в remind).

## 3. Протокол решений

Все решения — 2026-09-12/13, решения автора (в истории сессий захвачены
дословно; здесь переформулированы).

### 1. Киллер-фича: текст + зубы

База знаний не должна быть «просто текстами»: текст + хук-модификаторы devst +
«линтинг без установленного в проекте линтера». Решение: каждая практика =
текст (чеклист/скилл) + опциональные машинные чеки; обязательный этап — разведка
границ скорости (№2).

### 2. Правило скорости: потолок 1с, никого не резать молча

Резать больше чеков — меньше пользы тулзы. Потолок хуковой проверки — 1 секунда;
чек, который не влезает, НИКОГДА не режется молча — агент приносит замеры
(дифы 10/100/1000 строк) и спрашивает автора «а точно ли норм будет?»; решение
только за автором.

### 3. Жёсткость: гибрид C

Warn-only на старте; severity каждого чека — данные (не код); эскалация в
strict — позже per-project конфигом. Конфиг самодокументируется: у каждого
ключа — комментарий «зачем и почему» (шаблон devst.json + доки).

### 4. Канон: общее — в devst, проектное — в проектах; старые репы устарели

Общие практики становятся каноном devst (вшиты бинарными ассетами, ADR-018);
проектно-специфичные живут в проектных доках. Материалы внутренней методологии
dev-standard и парковочной репы дальних идей считаются устаревшими: провести
salvage ценного, затем удалить их — задача **T-17** (механику проверки
STANDARD_VERSION сделать самодостаточной внутри devst).

### 5. Большие практики: папки-скиллы, devst — установщик

Практика = папка-скилл (формат скилла devst: SKILL.md + файлы + малые чеки);
`devst kb install/remove/list` ставит/снимает их в харнессе (таргеты как у
integrations); per-project состав — в devst.json; чеки при нарушении ссылаются
на скилл («смотри скилл X»).

### 6. Каталог «линтинг без линтера» — самая низкая срочность

Минимальный набор чеков (секреты в диффе, TODO без T-NN, следы отладки, грубые
лимиты длины файлов) — последними в очереди; всё в той же декларативной системе.

### 7. Эвристика тестов: сначала умный маппинг (B)

Сначала B — маппинг «изменённый модуль → покрывающий тест» (соглашения имён +
скан импортов тест-каталогов, замер по правилу №2); при провале — A (диф-
эвристика «src без тестов») + C (вердикт `tests` в гейте закрытия задачи,
[фича 04](./04-task-registry.md)); со стоящей пометкой «всё равно надо потом»:
A+C со временем добавить в любом случае.

### 8. Доставка: установщик + напоминатель скиллов; `devst kb` — дополнение; SessionStart несёт малые части

Основной канал — установка/снятие скиллов + напоминания remind-провайдером
([фича 05](./05-reminder-system.md)); `devst kb` (list/show) — дополнительный
ручной вход; состав per-project — в devst.json; SessionStart несёт one-liner'ы
активных практик.

### 9. Кастомизация паков нужна (боль: ИИ никогда не используют Omit)

Даже самые умные модели избегают Omit и прочих удобств TS и обычно плодят новые
типы, разрушая существующие связи данных. Решение: кастомизация — часть
дизайна: паки лежат в доступном месте (каталог доступных практик + свои),
author-editable; первый образец — пак **ts-idioms** (Omit/Pick/satisfies/вывод
типов вместо дублирования) как собственный пак автора, правится руками без
пересборки devst.

- [ ] 2. Напоминатель: SessionStart one-liner'ы активных практик + «смотри скилл

- [ ] 4. Пак ts-idioms (№9) — образец и польза сразу.
- [ ] 5. Каталог «линтинг без линтера» (№6) — самая низкая срочность.
- [ ] 6. Разведка границ скорости — систематические замеры (дифы 10/100/1000
      строк), отчёт автору «а точно ли норм будет?» по каждому пограничному чеку.

## 5. НЕ-цели

- Замена установленных в проекте линтеров (ESLint и т.п.) — devst работает там,
  где их нет; конфликты решаются kb.off.
- Свой ИИ-отбор релевантности внутри devst (принцип fallow «no AI inside») —
  отбор механический (per-project конфиг); суждение остаётся за агентом.
- Интеграции Trello/Jira — будущее, отдельные решения (концепция, architecture/01).
- Подавление напоминаний («видел — не показывай») — по-прежнему вне охвата
  (требует хранимого состояния).
