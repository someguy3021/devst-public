# Feature 13: верификация только через UI-подтверждение — агент не может ставить verified

> Русский · [English](../../features/13-ui-only-verification.md)

> **Статус:** Реализовано (этапы 1–2; агентский путь закрыт Rust-IPC) · **Обновлено:** 2026-10-09
> **Суть:** режим проекта `devst.json → verifyMode: "ui-required"`: CLI-флаг
> `task close --verified` не пишет уровень, а создаёт pending-запрос; человек
> подтверждает в Tauri-окне (диалог с деталями задачи и срезом тулз) — уровень
> пишет только UI-путь (Rust-IPC). Планка автора: «Даже самый глупый агент ПРОСТО НЕ МОГ указать, что юзер проверил».
> **Ключевые факты:**
> - Дефолт `verifyMode: "open"` — поведение [фичи 11](./11-task-tags-and-verification.md) без изменений.
> - Сам close не блокируется ([ADR-010](../decisions/adr-010-detect-dont-block.md)): задача закрыта с verify=none; pending-запрос ждёт человека.
> - Уровень пишет только Rust-команда verify_approve (Tauri-IPC), до которой shell-агент не дотягивается.
> - Барьер от глупости и забывчивости — честно: не от злонамеренного агента с файловым доступом.
> **Связанное:** [фича 11](./11-task-tags-and-verification.md) (закрываемая дыра: `--verified` в CLI —
> «человеческий жест по определению», но технически агент может его подставить) ·
> [фича 12](./12-activity-journal.md) (activity-события) · [фича 03](./03-devst-ui-desktop-window.md) (окно) ·
> [ADR-020](../decisions/adr-020-tauri-sidecar.md) (UI зовёт CLI через сайдкар)

## Сценарии

1. `verifyMode: "ui-required"`; агент: `task close 5 --verified skim` → CLI создаёт
   pending {task, level, requested_by, slice} и отвечает: «запрос создан (REQ-a1b2) — ждёт
   подтверждения в devst-ui». Задача закрыта, verify=none — агент честно сообщает, а не притворяется.
2. Человек открывает окно → бейдж pending → диалог: детали задачи + срез тулз +
   выбор уровня (подтвердить предложенный или поменять) → «Подтверждаю».
3. Rust verify_approve пишет уровень (и activity-событие [фичи 12](./12-activity-journal.md)) → pending снят.
4. Отклонение → verify остаётся none + activity-событие `verify.rejected`.
5. `verifyMode: "open"` (по умолчанию) — поведение [фичи 11](./11-task-tags-and-verification.md) без изменений.

## Как устроен барьер

- `verifyMode: "ui-required"` в devst.json проекта; в этом режиме CLI-флаг `--verified`
  создаёт pending-запрос в базе реестра (миграция) и НЕ пишет уровень.
- Уровень пишет только Rust-команда verify_approve (Tauri-IPC) — shell-агент до неё
  не дотягивается; verify_list кормит бейдж pending в окне.
- До подтверждения задача видна в audit как none — работу агента посреди пути не блокируем ([ADR-010](../decisions/adr-010-detect-dont-block.md)).

## Что видит человек

Диалог показывает титул, объекты и дифф-стат задачи плюс машинный срез (риск / blast /
health-находки) и предложенный агентом уровень; человек подтверждает предложенный или
меняет его. Отклонение = verify остаётся none + activity-событие.

## Честные границы

Барьер — от глупости и забывчивости, не от злонамеренного агента с файловым доступом
(базу можно править руками) — говорим открыто в не-целях, не прячем. Tauri-окно
обязательно: без окна режим не имеет смысла (doctor предупреждает).

## НЕ-цели

- Не защита от злонамеренного агента с доступом к файлам.
- Не подтверждение через терминал/чат-кнопки — только Tauri-окно.
- Не блокировка close и не блокировка работы агента ([ADR-010](../decisions/adr-010-detect-dont-block.md)).
- Не удалённое подтверждение (пуш на телефон и т.п.) — локальное окно.

## Версии

### Реализовано (этапы 1–2)

- Конфиг verifyMode + pending-таблица (миграция базы реестра) + CLI: `close --verified`
  в ui-required → pending + сообщение.
- Rust verify_approve/verify_list + UI: бейдж pending, диалог подтверждения с деталями и срезом.

### Впереди (этапы 3–4)

- Activity-события verify.approve/reject ([фича 12](./12-activity-journal.md)); audit
  учитывает pending; скилл: агент в ui-required сообщает о pending, не ждёт.
- Канон-синхрон (скилл / README / HELP / фикстуры) и ui-e2e диалога.
