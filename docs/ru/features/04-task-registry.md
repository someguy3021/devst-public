# Feature 04: трекер задач: реестр со связями и таймерами, гейты, board

> Русский · [English](../../features/04-task-registry.md)

> **Статус:** этапы 0–6 ГОТОВЫ (ADR-017; сессии 16–19); этап 7 — задача T-5 реестра · **Обновлено:** 2026-09-11

**Суть:** канонический реестр задач devst: задача — объект со связями, таймерами
и гейтами закрытия; реестр поглощает open-questions и TODO-учёт, а `devst board` —
живой срез «что надо делать». Ответ на систематический дрейф документации:
аудит внешнего TTRPG-проекта нашёл 15 устаревших фактов после одной недели
активной работы.

**Ключевые факты:**

- 19 решений протокола (№1–10 дизайн + №11–19 батарея хранения) на 8 этапов.
- Задачи рождаются в SQLite-реестре (`docs/registry.db`); папка `docs/tasks/` не создаётся никогда; проза остаётся md (ADR-017).
- Дефолтная severity — warn (детект, не блокировка — ADR-010); strict — осознанный opt-in (ADR-013).
- Гейты закрытия требуют вердикт по каждому связанному объекту (правка этой сессией / явный отказ / хвост-задача); хвосты становятся новыми задачами — система замыкается на себя.
- `devst board` (алиасы: show-tasks-board, show-tasks-board-short) читает реестр живьём; карта и панель «Сейчас» — только указатели.

**Связанное:** [ADR-017](../decisions/adr-017-hybrid-storage-md-sqlite.md) (этап 0; отдельный ADR-018 «Трекер задач» не заводится — решение №19) · [ADR-010](../decisions/adr-010-detect-dont-block.md) / [ADR-013](../decisions/adr-013-default-deny.md) (warn / strict-opt-in) · [фича 03](./03-devst-ui-desktop-window.md) (доска в UI, DnD, apply-трансформеры) · [фича 05](./05-reminder-system.md) (reminder-провайдер «задачи протухли») · [ADR-015](../decisions/adr-015-tauri-ui-stack.md) · аудит дрейфа доков на внешнем TTRPG-проекте (2026-09-11) · roadmap 2.1, 2.2/2.3

## 1. Суть и потребители

| Потребитель | Как пользуется |
|---|---|
| Автор | руками в доках состояние не пишет: его видно на `devst board` / UI-доске; гейты требуют фиксацию за него |
| ИИ-агент | главный писатель: кристаллизация чатов → вопрос/хвост-задачи; работа через `task new/close` + `board`; гейты принуждают сводить статусы и доки |
| Будущие проекты | тот же реестр поверх той же тулзы; без тулзы — фолбэк open-questions.md (тир T1) |

## 2. Сценарии

1. Начало работы: `devst board` — протухшие сверху, потом срочные; агент (или
   автор в UI) берёт задачу, читает её связи и снимок состояния.
2. Кристаллизация чата: планирование/анализ происходит в ИИ-чате → по итогам
   агент создаёт вопрос/хвост-задачи с формулировками автора и связями на доки —
   «всё = задачи».
3. Работа над задачей: `task new` фиксирует связи «часть»/«объекты» и снимок
   состояния связанных доков; коммиты несут `Closes T-NN`.
4. Закрытие задачи: гейт перечисляет связанные объекты и требует вердикт по
   каждому — правка этой сессией / явный отказ с причиной / хвост; хвост сам
   становится новой задачей, привязанной к тому же объекту.
5. Закрытие сессии: гейт требует сведённые затронутые задачи, хвосты = T-NN
   или «хвостов нет», свип-вопрос про другие доки; strict ругается громко.
6. Вопрос разрешён: закрытие вопрос-задачи требует указать, куда легло решение
   (ADR / протокол фичи / architecture).

## 3. Протокол решений

Все решения — 2026-09-11, захвачены из чата автора; для этой страницы
переформулированы.

### 1. Диагноз: туду-листам не хватает системы

Автор хотел таск-трекинг «как система уровня Jira, со статусами и т.д.». Решение:
строим канонический трекер. Разбор: статусная доска сама дрейф не ловит (карточка
протухает так же, как строка туду-листа); ядро Jira, которое работает, —
идентичность задач (ID), единый реестр, связка с коммитами. Внешний трекер
отвергнут: истина вне канона, агенты без API слепы, git-история реестра теряет
смысл.

### 2. Жёсткость: таймеры у всего, система — база

Долг накопился за дни, а не месяцы — значит, никаких постепенных «шагов»:
система поставляется целиком. Возраст — вычисляемое свойство каждого объекта
(таймеры, §7): протухание — не мнение, а данные. Дефолт warn
([ADR-010](../decisions/adr-010-detect-dont-block.md)), strict — осознанный
opt-in (прецедент [ADR-013](../decisions/adr-013-default-deny.md)).

### 3. Хранение: гибрид, реестр задач — в БД с рождения

Проза (architecture/features/decisions/roadmap/тела log) остаётся md;
структурированные реестры переезжают в БД по одному — freeze → сессии-индекс →
задачи. Задачи рождаются сразу в БД-реестре: md-папки tasks/ не существует
(этап парсинга md-шапок отпадает). Бремя ритуала — полностью на агенте и тулзе.
«Боль в локах» автора → транзакции БД решают параллельную запись двух чатов
внутри одной ветки лучше файловых замен. Рамка хранения решена —
[ADR-017](../decisions/adr-017-hybrid-storage-md-sqlite.md); батарея хранения —
решения №11–19 ниже.

### 4. Захват планирования из чатов: «всё = задачи»

Захват = создание вопрос/хвост-задач с формулировками автора (длинные
размышления — тело задачи или связанный research-док); «задачи из ЭТОГО
источника» = поле «источник» в задаче плюс фильтрация по нему; «тулза
неизбежно потребует „готово“» = гейты закрытия задачи и сессии (§7). Изначально
предложенный тип «доков-обсуждений» отозван — тупик зафиксирован в §5 (НЕ-цели).

### 5. Задача — носитель связи, а не строка списка

Схема объекта с полями «часть»/«объекты» + автоснимок состояния при создании
(§6); флоу «понять → записать → решить → поймать изменения» (§6–7); связи задач
ловят заявленный дрейф точно и поимённо, линты — незаявленный сеткой (§7).
Туду-листы теряли связь потому, что связь жила в голове и в прозе;
объект-задача хранит её машинно.

### 6. Команда board: живой срез работы

`devst board` — живой срез реестра, скилловый формат (§8). Имя подтверждено
(№15): `devst board` — в стиле CLI (check/status/map/brief); длинные
`show-tasks-board[-short]` — алиасы
([ADR-017](../decisions/adr-017-hybrid-storage-md-sqlite.md)).

### 7. open-questions — это тоже задачи

kind «вопрос»; закрытие вопрос-задачи требует указать, куда легло решение
(ADR / протокол фичи / architecture) — существующая дисциплина «решённое
переносится с датой» становится принудительной. OQ.md при тулзе мигрирует в
реестр; в стандарте остаётся фолбэком T1/бес-тулзного режима (§10).

### 8. Приборы дрейфа: связи + линты

Обсуждение с агентом, одобрено автором («выглядит как надо», 2026-09-11):
заявленный дрейф ловят связи задач (точно, поимённо), незаявленный — doc-rot
линты («метрика-без-даты», «дока-старше-кода», свип-вопрос в DoD) — сеткой.
Хвосты гейтов становятся задачами — система замыкается на себя.

### 9. Файл-лог задачи: прикрепить задетые файлы

Поле touch на задаче (§6) — краткий git-derived лог: stat без диффов (диффы
принадлежат git; «не лезть в коммит» = лог даёт масштаб, хэш рядом). Гейт
закрытия сверяет декларацию («объекты») с фактом (touch) — механическая ловля
попутных эффектов (паттерн P1 аудита). Граница с графом: MVP — чистый git и не
ждёт roadmap 2.1; символьный уровень — следующий этап графа, файл-лог — его
первый потребитель-заказчик (вписан в roadmap 2.1).

### 10. Досье файла: обратный запрос для всех файлов

`devst file <путь>` — досье, вычисляемое по запросу из источников правды (§9):
«нужно всем файлам» обходится без новых сущностей и без хранения аннотаций при
файлах. «Когда говорить агенту» — три точки интеграции (§9): протокол поиска,
жизненный цикл задачи, freeze-хук. Одобрение автором: пара «протокол поиска +
жизненный цикл задачи» названа «просто супер».

### 11. Батарея хранения №1: UI-доступ к БД — Rust-сторона

Реестр в Tauri-UI живёт на Rust-стороне (rusqlite + Tauri-команды, IPC): нет
lost-update (один писатель, транзакции в одном процессе), файл БД никогда не
держится в памяти webview. Цена — дополнение
[ADR-015](../decisions/adr-015-tauri-ui-stack.md) («ядро в webview без IPC»):
появляется IPC-грань реестра, append-only; проза идёт через fs-плагин, экраны
через KernelAdapter не меняются. Отвергнуты wasm/sql.js (in-memory + запись
файла целиком — lost-update двух писателей, та самая «боль в локах»). Развилка
целиком — [ADR-017](../decisions/adr-017-hybrid-storage-md-sqlite.md), ось 2.

### 12. Батарея №2: маппинг root ↔ doc root — конфиг док-репы; реестр проектов машины не делаем

Дефолт — доки в корне проектной репы (маппинг не нужен); док-репа сама несёт
конфиг: путь проекта + placement. devst.json в проекте — сознательно не
механизм (в режиме «без следов» это был бы запрещённый след). Реестр проектов
на машине сейчас не строится — второй его потребитель (мета-доска) припаркован
среди дальних идей; вернуться при живой мета-доске. Опции —
[ADR-017](../decisions/adr-017-hybrid-storage-md-sqlite.md), ось 4.

### 13. Батарея №3: порядок миграции подтверждён

freeze → сессии-индекс → задачи — от самого болезненного (правка md-таблицы,
наблюдение в решении №3) к новому; задачи рождаются в БД, md-папки tasks/ не
существует. Усиление решения №3; зафиксировано в
[ADR-017](../decisions/adr-017-hybrid-storage-md-sqlite.md).

### 14. Батарея №4: TTL-дефолты и severity подтверждены

30д (задача открыта) / 7д (в работе) / 5д (метрика в доке) / 14д
(дока-старше-кода) — старт (§7); калибровка по метрике медианного возраста
дрейфа (база ~8 дней, аудит внешнего TTRPG-проекта) — этап 7. Дефолтная
severity — warn ([ADR-010](../decisions/adr-010-detect-dont-block.md)), strict —
осознанный opt-in (прецедент [ADR-013](../decisions/adr-013-default-deny.md));
конфиг — этап 5.

### 15. Батарея №5: имя команды — `devst board` + алиасы

`devst board` в стиле CLI (check/status/map/brief); алиасы show-tasks-board /
show-tasks-board-short — формулировка решения №6 продолжает работать. Развилка
закрыта ([ADR-017](../decisions/adr-017-hybrid-storage-md-sqlite.md)).

### 16. Батарея №6: cloud-save — дефолт выключен

Пуш док-репы в приватную remote — явное per-project решение автора (конфиг
док-репы); в проектный remote в режиме «без следов» док-репа не попадает
никогда — инвариант [ADR-017](../decisions/adr-017-hybrid-storage-md-sqlite.md)
не нарушается.

### 17. Батарея №7: devst мигрирует на себя — после этапов 1–2

Этап 6 идёт отдельной сессией после этапов 1–2: миграцию делает тулза
(`task new/close`, `board`), не руки; заводить задачи в БД до появления команд —
против духа решения №3 («бремя ритуала — полностью на агенте и тулзе»).

### 18. Батарея №8: иных болей хранения нет

Оси вопроса хранения (скорость парсинга, целостность, удобство ведения) + локи +
хостинг покрыты решениями №1–10 и №11–19
([ADR-017](../decisions/adr-017-hybrid-storage-md-sqlite.md)); остальное
вскрывается в работе этапов.

### 19. Один ADR-017 вместо отдельного ADR-018 «Трекер задач» — развилка закрыта

Этап 0 закрывает **один**
[ADR-017](../decisions/adr-017-hybrid-storage-md-sqlite.md); развилки
хранения/хостинга/миграции живут в его Опциях; «почему такой трекер» — протокол
№1–10 здесь (единственное место учёта — дубль в отдельном ADR стал бы вторым
местом учёта, паттерн P3 аудита, урок тупика «обсуждений»). Пометка развилки
продублирована в трёх видимых местах: шапка ADR-017 (Суть) · строка этапа 0
(§4 ниже) · log-запись сессии 16. Самостоятельный ADR о трекере появляется
только по будущей реальной развилке, не задним числом.

## 5. НЕ-цели

- Внешний трекер / Jira-сервис: истина вне канона, агенты без API слепы,
  git-история реестра теряет смысл.
- БД для прозы: тела architecture/features/decisions/roadmap/log остаются md —
  диффы, мержи и git-археология (`git log -S`) — живая ценность именно прозы
  (метод аудита внешнего TTRPG-проекта на них построен).
- Папка `docs/tasks/` не создаётся никогда: задачи рождаются в БД-реестре.
- Тип доков «обсуждения» — ОТКЛОНЁН (тупик, 2026-09-11): дублировал точки
  захвата (open-questions / протокол фичи / опции ADR / research) и добавлял
  четвёртое место учёта поверх и без того слабой связки. Автор: «Ты создаёшь
  больше сущностей, тогда как мы уже выяснили, что их текущая связка работает
  плохо». Захват чатов = вопрос/хвост-задачи + research-доки.
- Мета-доска всех проектов и реестр проектов на машине — отдельные идеи, в эту
  фичу не входят.
- Жёсткий дефолт: strict включается осознанно; дефолт — warn (ADR-010).

## 6. Объект «задача»: поля и жизненный цикл

| Поле | Что несёт |
|---|---|
| id | T-NN, сквозной по репе (вариант «по-докам» 02-01 отклонён: задачи не привязаны к одному доку) |
| kind | работа (сделать) · вопрос (решить) · хвост (авто-задача дрейфа из гейтов) |
| статус | открыта → в работе → решена (дата, коммит) / отклонена (дата); вычисляемый флаг «протухла»; маркер «ждёт: …» (автор/событие) |
| срочность | приоритет для сортировки board |
| часть | иерархия: фича NN/этап M, architecture NN, область |
| объекты | доки docs/… и пути кода src/…, чью правду задача меняет |
| снимок | HEAD репы + «Обновлено»/git-даты связанных доков; автомат в `task new`; предусловие закрытия |
| источник | откуда задача: чат (дата), фича, миграция OQ |
| тело | формулировка; длинные размышления — связанный research-док |
| touch | файлы, задетые задачей, — факт после работы: git-derived stat (путь · A/M/D · +N/−M · коммит); пересобираемое производное, диффы не хранятся |

Жизненный цикл (флоу автора, решение №5): **понять** (что проекту нужно) →
**записать** (связи + снимок: «ОНИ В ТАКОМ СОСТОЯНИИ СЕЙЧАС») → **решить**
(коммиты `Closes T-NN`) → **закрыть** (гейт: поймать изменения каждой связанной
сущности и зафиксировать их). Задача без связей допустима — помечается
«голая» (мягкое напоминание, не warning: связи — главная ценность).

Карточка в board-формате:

```
T-14 · работа · СРОЧНО · протухла (7д/7д)
  Гейт закрытия сессии: сверка Closes и статусов задач
  часть: фича 04/этап 3 · код: src/sessions.ts, cli.ts
```

Карточка в `task show` (--full):

```
T-12 · вопрос · ждёт автора · возраст 1д
  Хранение: выбрать порядок миграции реестров (freeze→сессии→задачи)
  источник: чат 2026-09-11
  объекты: docs/open-questions.md · связанные: ADR-015
  снимок: HEAD 1c19837 · open-questions.md обновлён 2026-09-10
```

## 7. Гейты и таймеры

Гейт закрытия задачи — вердикт по каждому связанному объекту:

1. правка этой сессией (док обновлён, его дата свежее снимка) — ок;
2. явный отказ с причиной («затронут только код; доке нечего менять, потому
   что…») — ок;
3. хвост — не теряется никогда: становится новой задачей (kind хвост),
   привязанной к тому же объекту («док X не отражает T-NN»).

Сверка «декларация ↔ факт» (§9): touch против связей «объекты» — затронуто
недекларированное → «попутный эффект» + досье всплывшего файла (агент выбирает:
хвост-задача или явный отказ); декларировано и не затронуто → «декларация не
подтверждена» (задача не та или связи кривые).

strict: закрытие без вердиктов блокируется.

Гейт закрытия сессии (CLI-запись log + форма закрытия сессии фичи 03, этап 5):

- затронутые задачи перечислены; для «решена» — коммит и обновлённый статус;
- хвосты = T-NN или «хвостов нет»;
- авто-строка файл-лога сессии: «файлы: +N/−M по K файлам» (дифф-стат коммитов
  сессии);
- свип-вопрос: «какие факты в других доках мой коммит делает неправдой?» +
  готовая подсказка `grep -rl <символ> docs/` по топ-символам диффа сессии;
- `Closes T-NN` в коммитах сверяется со статусами задач (расхождение в обе
  стороны — warning);
- если сессия кристаллизовала чат — вопрос/хвост-задачи созданы.

Таймеры (дефолты подтверждены — решение №14,
[ADR-017](../decisions/adr-017-hybrid-storage-md-sqlite.md); калибровка по
метрике дрейфа — этап 7):

| Объект | Отметка | Дефолт | Кто видит |
|---|---|---|---|
| задача «открыта» | дата создания | 30 д → warning | board / check |
| задача «в работе» | дата перевода | 7 д → «закрой или верни» | board / check |
| вопрос без движения | последняя правка | 30 д → «решай или отклоняй» | board / check |
| хвост без владельца | создание | 14 д | board |
| число/метрика в доке | (дата) рядом с числом | 5 д | линт «метрика-без-даты» |
| шапка дока «Обновлено» | vs git-даты упомянутых путей src/ | > 14 д | линт «дока-старше-кода» |
| реестр vs git-активность | коммиты ≥ K при 0 движений задач | — | «доска отстала от кода» |

Разделение труда детекции: связи задач ловят заявленный дрейф (точно); линты и
свип-вопрос ловят незаявленный (сеткой).

## 8. Команда board

`devst board` (алиасы: show-tasks-board, show-tasks-board-short) — живой срез
реестра, отвечающий на «что надо делать» в момент вопроса. Карта и панель
«Сейчас» — указатели, они протухают между сессиями; доска читает реестр живьём.

- формат — скилловый: из одной строки понятно, читать ли `task show T-NN`
  (прогрессивное раскрытие, §5.1 стандарта);
- сортировка: протухшие → срочность → возраст;
- дефолт — короткий формат; `--full` — тела, связи, снимки, история;
- место в контракте агента: стандарт §5.4 «что делать дальше» → `devst board`;
  панель «Сейчас» несёт строку-указатель «Задачи: N открытых, M протухли —
  devst board» (истина живёт в реестре; панель — чистые указатели).

## 9. Файл-лог задачи и досье файла: декларация ↔ факт ↔ обратный запрос

Два направления одной машины (решения №9–10):

**Вперёд — touch на задаче (§6):** связи «объекты» — декларация до работы;
touch — факт после; гейт закрытия сверяет их (§7). Краткий лог «какие файлы
задела эта задача» — чтобы не лезть в коммит; за деталями — хэш рядом.

**Назад — досье файла:** `devst file <путь>` — «а что с этим файлом вообще было
связано?» для любого файла, включая удалённые и переименованные
(`git log --follow`). Вычисляется на лету из источников правды; при файлах
ничего не хранится:

| Источник | Что даёт | Граф? |
|---|---|---|
| git --follow | история: коммиты, добавлен/удалён/переименован, +/− по жизни | нет |
| реестр задач | задачи-декларации («объекты», вкл. открытые = планируемая работа) + задачи-факты (touch) | нет |
| доки | упоминания пути (grep); упоминания символов файла — точно | пути — нет; символы — да, 2.1 |
| ui-freeze реестр | вердикт 🔒🔒/🔒/❓ — перед правкой видно заморозку | нет |

- удалённый файл, всё ещё упомянутый в доках = авто-детектор дрейфа;
- зеркальный вид той же машины — «что происходит вокруг этой доки» (открытые
  задачи на её зону, свежесть её фактов); вместе с board это почти `rot`-отчёт
  из аудита;
- жёсткое правило: досье — read-only вычисляемый вид; аннотации при файлах не
  хранятся (иначе четвёртое место учёта — тупик «обсуждений», §5).

Три точки интеграции — «когда именно говорить агенту» (по нарастающей шума):

1. Протокол поиска (§5.4 стандарта): «известен файл → `devst file`» — замена
   ручной grep-археологии; ад-хок сценарий «нашёл старый файл». Ноль шума.
2. Жизненный цикл задачи: при создании — автоподсказка связей «объекты» из
   досье (лечение «голых» задач); при закрытии — попутчик из сверки → досье
   всплывшего файла → осознанный выбор «хвост или отказ».
3. Freeze-хук ([ADR-011](../decisions/adr-011-ui-freeze.md) /
   [ADR-013](../decisions/adr-013-default-deny.md), точка принуждения уже
   существует): при блокировке/ворнинге отвечает строчкой досье — почему
   заморожено, где запись реестра, какая задача открыта. Анти-паттерн: НЕ
   показывать досье на каждую правку (шум и выжженный контекст).

Граница с roadmap 2.1: path-уровень (всё выше) — без графа, не блокируется;
символьный уровень (упоминания символов файла в доках, переименования символов,
`devst sweep`) — после переезда графа; досье — его потребитель (список
заказчиков вписан в roadmap 2.1).

## 10. Реестр поглощает open-questions

- вопрос = «не решено, надо решить» — та же единица работы: срочность, таймеры,
  связи. Аудит показал: OQ-записи гниют как тудушки (кейсы №6 и №7 — вопрос
  закрыт реальностью, запись висит); приборы должны быть общими.
- гейт закрытия вопрос-задачи: указать, куда легло решение (ADR / строка
  протокола фичи / правка architecture).
- длинные рамки и дословные хотки автора — тело задачи или связанный
  research-док; реестр несёт формулировку и связи (большие тела прозы
  остаются md).
- OQ.md: при тулзе мигрирует в реестр и закрывается надгробием-указателем;
  в стандарте остаётся фолбэком тира T1 / бес-тулзного режима (стандарт
  тул-опционален).
- линт «OQ застыл» из предложений аудита — сознательно не реализован: возраст
  каждой записи видит реестр.

## 11. Хранение реестра

Решено — [ADR-017](../decisions/adr-017-hybrid-storage-md-sqlite.md) (батарея
хранения, решения №11–19); здесь — выжимка.

- реестр задач — в БД с рождения (гибрид: канон-проза = md, реестры = БД;
  порядок миграции freeze → сессии-индекс → задачи — решения №3 и №13).
  md-папки tasks/ не существует.
- связи и снимки — реляционные данные (task_links: задача → объект, род связи,
  снимок состояния); в md это была бы ещё одна ручная таблица — анти-паттерн
  P3 из аудита.
- транзакции + один слой записи + optimistic concurrency решают параллельную
  запись двух чатов внутри одной ветки лучше файловых замен (боль «локов»
  автора); WAL-дисциплина: чекпоинт перед коммитом (хук), `-wal`/`-shm` вне
  гита.
- CLI — node:sqlite (zero-deps; требуется Node ≥ 22.5). Хранение UI решено
  (решение №11): Rust-сторона — rusqlite + IPC;
  [ADR-015](../decisions/adr-015-tauri-ui-stack.md) дополнен «БД-гранью
  реестра»; wasm/sql.js отвергнуты (lost-update при записи файла целиком).
- хостинг канона — режимная модель (ADR-017, ось 3): репа проекта (по умолчанию) /
  сопроводительная док-репа: сосед `../name.docs/` (дефолт) или вложенная
  (`my-docs/`, placement-флаг) со своей git-репой; невидимость —
  `.git/info/exclude` или глобальные excludes (не .gitignore). Инвариант
  «без следов»: docs и AGENTS не в истории проектной репы и не в её пуше;
  AGENTS-в-корне + gitignore — opt-in, не дефолт. Маппинг root ↔ doc root решён
  (решение №12): конвенция «доки в корне» + конфиг в самой док-репе; реестр
  проектов машины не делаем. Cloud-save — пуш в приватную remote: дефолт
  выключен, per-project (решение №16).

## 12. Влияние на стандарт и тулзу (стандарт: готово — v1.6, 2026-09-11; тулза: этапы 1–5)

Правки методологии dev-standard (любая правка — версия + дата в её README):

- §1: «что должно существовать» = roadmap + реестр задач; TODO-секции в
  architecture-доках упраздняются (их место — задачи).
- §3: с тулзой — «задачи/вопросы живут в реестре трекера»; без тулзы —
  open-questions.md (фолбэк тира T1).
- §4.1: вход потока артефактов — реестр (идея/вопрос → вопрос/работа-задача);
  кристаллизация чата — ритуал захвата.
- §4.2 DoD: + «затронутые задачи сведены»; «хвосты = T-NN или „хвостов нет“»;
  свип-вопрос; кристаллизация чата записана.
- §5.3: панель «Сейчас» — строка-указатель на board; §5.4: «что делать дальше» →
  `devst board`; «известен файл» → `devst file <путь>`.
- §9: новых md-шаблонов нет (реестр — не md); OPEN-QUESTIONS остаётся фолбэком.

Тулза (devst):

- scaffold: NewKind += task; команды `task new/show/close`, `board`,
  `devst file <путь>` (досье);
- touch-индекс задачи (git stat) в ядре реестра; авто-строка файл-лога сессии
  («файлы: +N/−M») в записи сессии;
- check: Closes-сверка, валидация связей (пути/доки существуют), сверка
  «декларация ↔ факт» на закрытии задачи;
- doc-rot линты («метрика-без-даты», «дока-старше-кода») — roadmap 2.3, сетка
  поверх связей задач.
