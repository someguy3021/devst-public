# ADR-025: Связанные devst-репы: docs/links.json, ссылки id://, links check/pin/mirror

> Русский · [English](../../decisions/adr-025-linked-repos-links-json.md)

> **Статус:** принято (T-29) · **Дата:** 2026-10-06

**Суть:** механизм связывания раздельных devst-реп: обе стороны декларируют друг друга
в `docs/links.json`; маркдаун-ссылка на док соседа — `id://путь/док.md` (линтится); пины
sha256+HEAD сверяются `links check`; избранные логи соседа зеркалируются `links mirror`;
тезисы логов соседа видны в `links check`. Первый тест — пара «внешний TTRPG-проект ↔
общая репа-база знаний по ИИ-пайплайнам».

**Отвергнуто:** сабмодули/монореп (репы должны остаться раздельными, история не
переплетается); односторонние связи без взаимности (связь «в одну сторону» молча гниёт —
check репортит «сосед нас не заявил»); хаб-центричная схема §6.1 сейчас (peer-to-peer
работает без хаба, §5.8 — строительный блок для будущего хаба); зеркала внутри docs/log/
соседа (ломают панель «Сейчас» и проверки дублей чужой репы).

**Связанное:** [фича 07](../../features/07-linked-repos.md) ·
репа внутренней методологии (dev-standard) §5.8 (v1.8) · T-29

## Контекст

Внешний TTRPG-проект (T2, LLM-генерация ассетов) жёстко завязан на общую репу-базу
знаний по ИИ-пайплайнам. Репы раздельные; в доках TTRPG-проекта уже ≥6 ссылок на пути
базы знаний (голый текст, ничего не проверяет); серия сессий 110–115 — по сути кампании
по базе знаний, живущие в логах TTRPG-проекта; база знаний не была devst-репой только
потому, что не было механизма связей. Нужен общий механизм на будущее для любых пар реп:
связывание доков, логов, ресерчей + защита от утери.

## Решение

- **Манифест `docs/links.json`** в каждой из связанных реп: `neighbors[]` = {id, name,
  path (относительный!), role (producer/consumer/peer — роль соседа относительно нас),
  pins[], mirror[]}. Схема и валидация — [фича 07](../../features/07-linked-repos.md).
- **Синтаксис ссылки** `id://путь/док.md` — id как в links.json (например,
  `kb://workflows-tests/README.md`). Веб-схемы (https:// и пр.) — не соседи. Линтер:
  неизвестный сосед или отсутствующий файл — ошибки `ссылка-сосед`; битый манифест —
  `связи-невалидны`.
- **Команды** (пишут только в свою репу — сосед не трогается никогда):
  `links` (книжка), `links check [--json]` (доступность, взаимность, HEAD/dirty, тезисы
  логов соседа, коммиты с даты пина, статусы пинов, свежесть зеркал; не блокирует),
  `links pin [--id]` (sha256 файла/каталога без node_modules/.log + HEAD + дата),
  `links mirror [--id]` (байт-в-байт копии избранных файлов в свою `docs/mirror/<id>/`).
- **Правило домена** (репа внутренней методологии (dev-standard) §5.8): сессия про домен
  соседа живёт у соседа, у себя — указатель + тезис; зеркала — страховка для уже
  написанного.

## Обоснование

- Симметрия (взаимность) делает связь наблюдаемой: односторонняя связь — сигнал, а не
  норма.
- `id://` вместо голых путей: ссылки становятся кликабельными машинами проверки — то же,
  что `ссылка-битая` сделала для внутренних ссылок.
- Пины через sha256, а не только git-HEAD: сосед может быть не git-репой (portable-
  установка вне гита), а грязный worktree честно показывается отдельно («там работают —
  сверке не доверяй»).
- Зеркала вне секций: ноль спецслучаев в линтере доков, чужие номера сессий не мешают.

## Последствия

**Позитивные:** потеря любой репы пары не теряет истории (зеркала); дрейф знаний виден
(`ИЗМЕНИЛОСЬ с даты`); хендофф через границы реп (тезисы логов соседа); база знаний
вошла в стандарт как полноценная T2-репа без смены своей природы.

**Негативные / риски:** пины требуют ритуала (`links check` + `pin` в конце сессии) —
без него отстают, но это видно в отчёте; `match` зеркал — regex по имени, который можно
написать слишком широко (зеркалит лишнее) — лечится ревью одной строки манифеста.
