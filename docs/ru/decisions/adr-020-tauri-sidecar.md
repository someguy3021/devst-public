# ADR-020: сайдкар devst в Tauri-UI — task-мутации из окна через CLI

> Русский · [English](../../decisions/adr-020-tauri-sidecar.md)

> **Статус:** Принято · **Дата:** 2026-09-12

**Суть:** Tauri-окно везёт SEA-бинарь с собой (`externalBin: binaries/devst`, T-12):
доска получает «+ задача» и «✓ гейт закрытия» — мутации исполняет CLI-сайдкар
(`task new` / `task close`, cwd = открытая репа), гейты не дублируются в окне.
SidecarKernel — точечное расширение KernelAdapter (`taskNew`/`taskClose`), не полная
подмена DirectKernel.

**Отвергнуто:** полная SidecarKernel-подмена (чтение webview-ядром уже работает —
ADR-015); гейты в Rust (вторая реализация мимо 319 тестов); wasm/sql.js (ADR-017 №11).

**Связанное:** [ADR-015](adr-015-tauri-ui-stack.md) ·
[ADR-017](adr-017-hybrid-storage-md-sqlite.md) (№11 — ревизия) ·
[ADR-018](adr-018-sea-binary-distribution.md) · T-12 · roadmap 2.3.

## Контекст

Доска в окне умела только смену статуса через Rust-rusqlite; создание и закрытие
задач — только CLI. Гейты закрытия (вердикты на объекты, сверка «декларация ↔ факт»,
Closes-сверка) живут в ядре CLI с тестами — переносить их в Rust = вторая реализация.
После ADR-018 появился самодостаточный exe — возражение «сайдкар требует Node»
(Опции B в ADR-015) исчезло.

## Опции

### A. Сайдкар для task-мутаций, остальное как есть (выбрано)

- Плюсы: гейты одни — в CLI (реестр тестов работает на окно); окно остаётся
  «видом/редактором канона»; сборка = 2 файла (UI exe + CLI exe рядом).
- Минусы: spawn процесса на мутацию (~50–150 мс — для кнопки приемлемо); два
  sqlite-писателя реестра (см. Решение п.2).

### B. Полная SidecarKernel (все методы через CLI)

- Плюсы: один канал, максимум единообразия.
- Минусы: чтение/линт/freeze в webview-ядре уже работают без IPC; каждый вызов —
  процесс; переписывание DirectKernel без выигрыша. Остаётся за гипотетическим
  будущим, если webview-ядро начнёт расходиться с CLI.

### C. Гейты в Rust-стороне

- Плюсы: один процесс, один писатель.
- Минусы: вторая реализация домена мимо 319 тестов; двойной язык для одной логики —
  прямо против ADR-015.

## Решение

1. **Сайдкар**: `externalBin: ["binaries/devst"]` + плагин shell
   (`shell:allow-execute`, только этот sidecar); `pnpm ui:build` = `build:sea` →
   `scripts/sidecar-copy.mjs` (triple из rustc) → `tauri build --no-bundle`.
   Продукт — папка из двух exe.
2. **Писатели реестра — два, оба честные**: быстрые статусные операции доски (DnD,
   кнопки движения) остаются в Rust-rusqlite (ADR-017 №11), task new/close — через
   сайдкар (node:sqlite). Ревизия №11: её мотив «один писатель» был против
   wasm-схемы «файл целиком в памяти» (lost-update); два полноценных SQLite-писателя
   с транзакциями и WAL lost-update не создают. Задачи с гейтами — только через
   CLI; кандидаты на переезд в сайдкар потом: статусные операции (если появятся
   свои гейты).
3. **KernelAdapter**: `taskNew(TaskNewInput)` / `taskClose(id, TaskCloseInput)` →
   `TaskOpResult { ok, output }`; DirectKernel — спавн сайдкара (cwd = репа),
   MockKernel — in-memory мутации фикстуры + журнал вызовов (e2e).

## Обоснование

- Цель T-12 «2 exe как единое целое» достигается с минимумом нового кода: UI-диалоги
  (~60 строк) + спавн-обвязка (~30) — вся доменная логика уже в CLI с тестами.
- ADR-015 вариант B («мутации через CLI») исполнен там, где у него реальная цена —
  гейты, — без его минусов (Node больше не нужен).

## Последствия

**Позитивные:**
- Окно = полноценное рабочее место по задачам: создать, вести, закрыть с гейтом.
- Один источник доменных правил (CLI) для агента и окна.

**Негативные / риски:**
- Дистрибутив потолстел: рядом с UI exe живёт ~92 МБ сайдкар.
- Два писателя реестра — следить за WAL-дисциплиной (чекпоинт перед коммитом —
  за хуком CLI; Rust-сторона пишет короткими транзакциями).
- Спавн на мутацию — Windows Defender может добавить задержку на холодный старт.
