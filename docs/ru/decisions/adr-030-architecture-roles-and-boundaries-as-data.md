# ADR-030: архитектурные роли и границы как данные

> Русский · [English](../../decisions/adr-030-architecture-roles-and-boundaries-as-data.md)

> **Статус:** Принято · **Дата:** 2026-10-14
> **Суть:** архитектура репы живёт как машиночитаемая модель в
> `docs/architecture/arch.model.json`: роли-классификатор путей, матрица рёбер
> default-deny (настраиваемо), правила пакетов, контракты узлов с severity, пресеты по
> официальным rulebook'ам (FSD, Clean Architecture). `devst arch check` сверяет граф
> импортов с матрицей; канон-md и диаграммы — генерируемые проекции; `arch detect` —
> ИИ-первый, машинные эвристики — fallback.
> **Отвергнуто:** default-allow по умолчанию; валидация только как TS-библиотека без
> команды; хардкод дашборд-карт до появления модели (переехали в проекции).
> **Связанное:** [фича 16](../features/16-architecture-roles-and-boundaries.md) (реализация) ·
> [ADR-028](./adr-028-parser-cascade-t0-t1-t2.md) (граф, который проверяется) ·

## Контекст

«Что делать» и «как делать» в devst были решены; «как делать ПРАВИЛЬНО по
архитектуре» — нет: границы слоёв жили прозой в головах и доках, невидимые агенту, без
детекции дрейфа. Разведка предложила модель + конструктор; параллельная находка это
подтвердила: половина видов дашборда код-интеллекта — проекции такой модели и
строились дважды. Добил конкретный факт: резолвер графа не понимал tsconfig-алиасы
(`@/entities/user` резолвился во внешний пакет), так что FSD-репы были непроверяемы —
это стало этапом 0.

## Опции

### A. Хардкод-линтер: правила в коде, репы списком

- Плюсы: быстро.
- Минусы: каждый проект — правка кода devst; пресеты невозможны; дашборды строятся
  дважды.

### B. Модель как данные + генерируемые проекции (выбрано)

- Плюсы: конструктор (пресет + правки автора), канон/диаграммы/виды из одного
  источника, агент читает модель через MCP; синтаксис ролей/матрицы мал.
- Минусы: DSL надо держать маленьким (ползучесть — главный риск; критерий: каждое
  правило обязано выражаться через роли / рёбра / контракты / оверрайды).

## Решение

**Вариант B.** `arch.model.json` (строгий JSON, `schemaVersion`) в
`docs/architecture/`: роли (плоско + дерево, свой минимал-глоб, дубль globs — ошибка,
приоритет = литеральные сегменты), матрица рёбер default-deny (`defaultDeny`
настраиваем; циклы внутри роли — per-role флаг), правила «роль → разрешённые пакеты»,
контракты узлов (public API / нейминг / ассеты, `severity error|warn`, флаг `slices`
FSD). Пресеты `fsd` / `clean` / `empty` (по официальным rulebook'ам, clean-room)
вшиты в SEA-бинарь ассетами; `devst arch init --preset`. `devst arch validate` (модель)
и `arch check` (нарушения поверх графа: файл, правило, «почему», severity;
человекочитаемо + `--json`), плюс однострочная arch-строка в `devst check` и brief
сессии. Канон-md (роли + mermaid) генерируется — расхождение с моделью ловит check,
так что ручные правки детектируются, а не теряются. MCP `get_arch_model` — полный
аналог. `arch detect` — ИИ-первый, машинные эвристики — fallback. Этап 0 (сделан):
tsconfig-алиасы в резолвере графа — без них FSD-репы непроверяемы.

## Последствия

**Позитивные:** границы машиночитаемы и проверяются на настоящем графе; агент видит
роли с порога сессии; дашборд-карты строятся один раз — как проекции.

**Негативные / риски:** ползучесть DSL — держится критерием выразимости; алиасы
сложнее wildcard — неразрешённые честно репортятся; вкладка «Arch» в десктопе живёт
отдельно от «Код» до решения автора о слиянии.
