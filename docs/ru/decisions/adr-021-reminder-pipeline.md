# ADR-021: система напоминаний: провайдеры поверх детекторов, один рендер на носитель

> Русский · [English](../../decisions/adr-021-reminder-pipeline.md)

> **Статус:** Принято · **Дата:** 2026-09-12

**Суть:** все напоминания devst собираются чистым ядром `src/remind.ts`:
`Reminder {id, severity, title, detail?, action?}` + `collectReminders(факты, конфиг)`.
Один вход `devst remind [--json]`; SessionStart-хук, brief и UI-виджет «Сейчас»
только рендерят один массив. Кастомизация — слайс «remind» devst.json.

**Отвергнуто:** рукописные блоки в хуке (добавление = 4 точки правки — диагноз T-13);
журнал/подавление «видел» (нужно состояние — фича 05 НЕ-цели); пороги в коде.

**Связанное:** [фича 05](../features/05-reminder-system.md) ·
[ADR-010](adr-010-detect-dont-block.md) ·
[ADR-015](adr-015-tauri-ui-stack.md) · T-16.

## Контекст

Инвентаризация (2026-09-12) нашла пять семейств напоминаний: линт-правила check
(уже система), SessionStart-панель (6 рукописных python-блоков), brief (те же
сигналы третьим рендером), TTL-таймеры реестра (конфигурируемые), точечные
подсказки cli.ts. Добавление одного напоминания (T-13) потребовало правок в
четырёх местах; пороги вшиты; рендеры расходятся. Автор: единый класс «чтобы не
затерялось в 10 идентичных вариациях в разных местах кода», точка кастомизации на
будущее; «сделать хорошо но дольше».

## Опции

### A. Провайдеры поверх детекторов + носители-рендеры (выбрано)

- Плюсы: семантика в одном месте; существующие детекторы не переписываются
  (провайдер = отображение фактов → Reminder); хук упрощается до одного вызова;
  кастомизация конфигом; чистое ядро тестируется изолированно.
- Минусы: факты собирает обвязка (cli) — напоминания зависят от её качества;
  носители обязаны догонять новую форму (одноразовая миграция).

### B. Единый «inbox» с состоянием (журнал, подавление)

- Плюсы: можно «закрывать» напоминания.
- Минусы: хранение состояния — отдельная развилка (где, кто чистит); не запрашивалось.

### C. Оставить как есть + дисциплина

- Плюсы: ноль работы.
- Минусы: боль остаётся; каждая новая напоминалка умножает расхождение.

## Решение

1. Ядро: `Reminder`/`RemindConfig` (+`REMIND_DEFAULTS`), `parseRemindConfig`
   (слайс «remind»: auditDays=30, reqOpen=3, off=[]), `collectReminders` — 8
   провайдеров (conventions-errors с detail-строками правил, uncommitted,
   undocumented, baseline-drift, tasks-rotten, conventions-warnings — прячется за
   ошибками, req-open, audit), `renderRemindText` (⚠/⏰ + детали).
2. CLI: `devst remind [--json]`; сбор фактов — checkDocs + baselineDrift +
   undocData + collectUncommitted + таймеры реестра + метка аудита (общие
   хелперы с brief). brief: composeBrief принимает Reminder[] (блок «Напоминания:»).
3. Хук SessionStart: один вызов `remind --json` + один генерический python-рендер
   вместо четырёх блоков; freeze-гард остаётся файловым (контекстный).
4. UI: `KernelAdapter.remind()` (Direct — сайдкар `runCliJson`, Mock — фикстура),
   RemindersPanel на вкладке «Сейчас».

## Обоснование

- Ответ на прямой запрос автора: дополнять — провайдером, отслеживать — одним
  источником, кастомизировать — devst.json.
- «Хорошо но дольше»: детали ошибок сохранены (detail-строки), все три носителя
  и конфиг в одном проходе.

## Последствия

**Позитивные:**
- Новое напоминание = ~15 строк провайдера + запись в collectReminders + тест;
  хук/UI/brief подхватывают сами.
- SessionStart: 1 процесс вместо 3; панель единообразна.

**Негативные / риски:**
- Формулировки панели изменились (тесты/привычки) — старые строки заменены
  эквивалентными по смыслу.
- remind на репе без node ≥ 22.5 теряет tasks-rotten (реестр недоступен) —
  честная деградация, остальные провайдеры работают.
