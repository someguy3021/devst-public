# ADR-029: пункты ТЗ фичи — требования как данные с человеческой верификацией

> Русский · [English](../../decisions/adr-029-feature-spec-items-as-data.md)

> **Статус:** Принято · **Дата:** 2026-10-11
> **Суть:** требования фичи становятся машиночитаемыми пунктами с дословной
> цитатой-источником и связями-тегами на задачи; агент выполняет сам, но подтверждение
> пункта — жест человека через инбокс верификации (переиспользование
> [фичи 11](../features/11-task-tags-and-verification.md) +
> [фичи 13](../features/13-ui-only-verification.md)); три человеческие точки:
> верификация ТЗ до старта → подтверждение по ходу → закрытие/переоткрытие.
> **Отвергнуто:** линт содержания формулировок («с линтом вроде бы мимо»); жёсткая
> блокировка работ до ратификации ([ADR-010](./adr-010-detect-dont-block.md)); отдельная
> шкала ступеней для пунктов.
> **Связанное:** [фича 14](../features/14-spec-items-as-data.md) (реализация) ·
> [фича 11](../features/11-task-tags-and-verification.md) ·
> [фича 13](../features/13-ui-only-verification.md) ·
> [ADR-010](./adr-010-detect-dont-block.md) · [ADR-020](./adr-020-tauri-sidecar.md)

## Контекст

Решение произвёл реальный фейл: расплывчатые требования («хочу как у X») → агент
записал ТЗ «по минималке» и сам пометил выполнено → «20% от референса и видения, хотя
всё запускается». Вскрытие нашло два отсутствующих гейта: (1) полноту ТЗ никто не
ратифицировал до старта; (2) «выполнено» ставил сам исполнитель — требований как
сущностей не было, подтверждать было нечего. Третья: ручные чекбоксы этапов протухли в
обе стороны на сданной фиче. Механика человеческой верификации уже существовала на
уровне задач ([фича 11](../features/11-task-tags-and-verification.md): ступени доверия;
[фича 13](../features/13-ui-only-verification.md): ui-required, pending-инбокс) — она
не покрывала только уровень требований фичи.

## Опции

### A. Линт-правила в `check` («фича без приёмки = ошибка»)

- Плюсы: дёшево, движок есть.
- Минусы: проверяет структуру, а не волю автора; не решает ни «записал по минималке»,
  ни «сам поставил галку». Отклонено автором: «с линтом вроде бы мимо».

### B. Ритуал в скилле (агент всегда опрашивает автора перед фичей)

- Плюсы: ноль кода.
- Минусы: держится на дисциплине агента; вне харнесса devst не работает; фактов
  ратификации нет — нечем показать «это требование я подписал».

### C. Требования как данные + готовый human-inbox (выбрано)

- Плюсы: переносит доказанную механику (ступени, pending, Rust IPC, аудит) на уровень
  требований; истина в каноне (фича-дока, git-история); агенту — MCP-overview; решает
  обе боли — железное ТЗ через цитаты-источники и ратификацию, проверка по ходу через
  инбокс.
- Минусы: миграция реестра + парсер секции ТЗ + ветка инбокса в приложении; новые
  жесты подтверждения для автора (компенсируется прокси-опросами через агента).

## Решение

**Вариант C**, реализован как [фича 14](../features/14-spec-items-as-data.md): секция
`## ТЗ` в фича-доке — пункты `R1..RN` с ID (не переиспользуются), дословной
цитатой-источником (иначе — «выведено агентом») и связями-тегами на задачи
многие-ко-многим. Два статуса пункта: агентское «сделано» (доказательство обязательно)
и человеческое «подтверждено» (ступень доверия, актёр, дата). Три человеческие точки:
верификация ТЗ до первой рабочей задачи (жест «верифицировано / на доработку»,
частичная допустима, блокировка работы остаётся мягкой); подтверждение пунктов по ходу
через инбокс; `feature close` (все пункты подтверждены/отклонены/НЕ-цели, иначе
отказ; must-долги блокируют, should/could — задачи-переносы) и `feature reopen` с
фиксацией факта. `verifyMode` — полный аналог задач (дефолт ui-required — уровень
пишет только десктоп-приложение через Rust IPC). Удаление пунктов запрещено; смена
смысла после ратификации требует нового пункта-кандидата; правки автора идут через
агента с последующим подтверждением.

## Последствия

**Позитивные:** требования перестают быть прозой — у каждого пункта источник, статус,
история, связи; «сделано» без человеческой подписи не считается; длинные фичи (больше
двух сессий) получают непрерывность — срез подтверждённого живёт в реестре и приходит
агенту на старте сессии; ретро-перевод старых фич даёт честную карту долга (пилот сразу
вскрыл «20%»).

**Негативные / риски:** новый обязательный ритуал (верификация ТЗ) рискует «опять
бюрократией» — гасится прокси-опросами и мягкой блокировкой; два носителя истины
(markdown + реестр) могут расходиться — гасится двусторонним парсером и
формат-предупреждениями в `check`.
