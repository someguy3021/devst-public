# ADR-023: публичный docs-only релиз devst-public: сурс закрыт, EN+RU, бинарники в Releases

> Русский · [English](../../decisions/adr-023-public-docs-only-release.md)

> **Статус:** принято · **Дата:** 2026-09-25

**Суть:** публичный артефакт devst — отдельный репо `devst-public` с чистой историей:
курируемая документация (включая внутренние механизмы) на английском с русским
зеркалом + бинарники в Releases. Исходный код не публикуется никогда; приватная репа
остаётся единственным домом разработки.

**Отвергнуто:** открытие текущей приватной репы (сурс и личное — в git-истории) и
npm-дистрибуция исходников (фаза 2.2 roadmap в старой формулировке).

**Связанное:** T-25 (реестр задач: `devst task show T-25`) · roadmap, фаза 2.2
(релиз и масштабирование) · [ADR-018](adr-018-sea-binary-distribution.md) (SEA) ·
[ADR-020](adr-020-tauri-sidecar.md) (сайдкар).

## Контекст

- Цель — резюме: публичное, читаемое посторонним свидетельство инженерной работы
  (архитектура, решения, культура тестирования), а не распространение тулзы.
  Приоритет автора: «красиво» важнее «всё работает».
- Приватная репа `devst` на GitHub сейчас закрыта (анонимный запрос к API — 404,
  проверено 2026-09-25), сурс не засвечен. В истории — полный код и backup-ветки.
- Фаза 2.2 roadmap писалась под npm-дистрибуцию с исходниками; решение автора
  (чат 2026-09-25) меняет стратегию: сурс закрыт, публична только документация.
- Разведка утечек (2026-09-25): личные машинные пути минимум в 4 файлах; ~15
  упоминаний закрытого внешнего TTRPG-проекта по докам; ссылки ведут в закрытый
  соседний репо методологии — механическая публикация чего-либо из текущих доков
  небезопасна.

## Опции

### A. Открыть текущую репо `devst`

- Плюсы: ноль работы по переносу; звёздочки/issues сразу на коде.
- Минусы: полный сурс в истории (включая backup-ветки); личные пути и названия
  закрытых проектов в доках и `registry.db`; переписывание истории ради этого —
  риск без выгоды; противоречит решению автора «сурс не релизим».

### B. Отдельный публичный репо docs-only (чистая история) — выбран

- Плюсы: ноль риска утечки (в публичный репо попадает только то, что положили
  руками); чистая история; резюме-ценность — переведённые ADR и фичи показывают
  инженерную культуру без кода; исходники приватны навсегда, без оговорок.
- Минусы: двухранение истины — публичные тексты являются ручной производной
  приватных доков и будут дрейфовать; нужен санитизационный проход и
  стоп-паттерны как страховка.

### C. GitHub Pages из приватной репы (Pro-план)

- Плюсы: «сайт» выглядит наряднее репы.
- Минусы: не даёт главного резюме-артефакта (ссылки на сам репо); тянет сборочный
  стек; видимость Pages зависит от плана. Отложено, не отвергнуто: Pages можно
  добавить позже поверх того же контента `devst-public`.

## Решение

**Вариант B.** Публичный репо `devst-public` (создаёт автор лично), чистая
git-история, состав и правила:

1. **Курируемый корпус** (не зеркало приватных доков): EN-landing (README);
   адаптация методологии dev-standard — текст переписывается внутрь, ссылки на
   закрытый соседний репо убираются; архитектурный обзор; 6 фич как
   feature-страницы; все 22 ADR в переводе. НЕ публикуются: `docs/log/`, реестр
   задач, `open-questions.md`, `docs/research/`, `AGENTS.md`, `fixtures/`,
   `_drift/`, `src/`, `tests/`, код `ui/`, `integrations/`.
2. **Санитизация — кураторский перенос + стоп-паттерн-чек.** Публичные тексты
   пишутся заново по-английски (перевод приватного текста = новая редакция,
   приватные файлы не копируются механически); перед каждым пушем — grep-инвариант:
   личные машинные пути, кодовые имена закрытых проектов — 0 вхождений. Закрытые
   проекты в публичных текстах называются нейтрально («a TTRPG side project»)
   без имён репо и путей.
3. **Языки:** английский — источник истины, в корне репо; русский — зеркало в
   `docs/ru/`, переводит EN-редакцию (не приватный оригинал); в шапке каждой
   страницы — дата синхронизации.
4. **Лицензия** — CC BY 4.0: в репо только тексты и ассеты, код-лицензия не нужна.
5. **Бинарники — в GitHub Releases:** `devst.exe` (SEA, [ADR-018](adr-018-sea-binary-distribution.md))
   + `devst-ui.exe` (сайдкар, [ADR-020](adr-020-tauri-sidecar.md)); README явно
   говорит: неподписанные (SmartScreen предупредит), демо-проект для резюме,
   поддержка не обещается.
6. **CI публичного репо** — лёгкий воркфлоу: markdown линк-чек +
   стоп-паттерн-чек («ничего приватного не утекло»). CI-бейдж приватной репы не
   используется — бейджи приватных реп публично не рендерятся.
7. **Первый релиз** — тег `v0.5.0`, синхронно с версией в README приватной репы.

## Обоснование

- Для резюме важен рассказ «как я проектирую и веду documenting-культуру», а не
  код: ADR, фичи и методология это показывают лучше диффов.
- Кураторский перенос дешевле и безопаснее фильтрации: то, что не скопировано,
  не может утечь. Стоп-паттерны — страховка от человеческой ошибки, не основной
  механизм.
- Бинарники в Releases дают «кнопку Download» без вскрытия сурсов (SEA-бинарь
  самодостаточен, [ADR-018](adr-018-sea-binary-distribution.md)) — публикация
  бинарников не раскрывает исходники.

## Последствия

**Позитивные:**
- Исходники и личное физически не попадают в публичный репо; риск утечки сведён
  к «забыть в переведённом тексте» и закрывается стоп-паттернами + ревью перед
  пушем.
- Чистая история и полный контроль над публичным нарративом.

**Негативные / риски:**
- Дрейф: публичные тексты — ручная производная; правило — изменения приватных
  доков, затрагивающие публичный корпус, идут через задачу с обновлением зеркала
  (как T-25).
- RU-зеркало отстаёт от EN по построению; допустимый лаг отслеживается датами
  синхронизации в шапках страниц.
- Бинарники в Releases = обязательства отвечать на issues про них; в README явно
  прописываем «демо-проект, поддержка не обещается».
