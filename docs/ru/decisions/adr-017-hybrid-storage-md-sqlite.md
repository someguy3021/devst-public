# ADR-017: Хранение данных devst: гибрид md + SQLite, порядок миграции, хостинг

> Русский · [English](../../decisions/adr-017-hybrid-storage-md-sqlite.md)

> **Статус:** принято · **Дата:** 2026-09-11

**Суть:** канон — гибрид: проза остаётся md в git, реестры переезжают в SQLite
(`node:sqlite`, zero-deps) по одному — freeze → сессии-индекс → задачи; задачи рождаются
в БД; UI — Rust-сторона (rusqlite + IPC, дополнение ADR-015); хостинг — репа проекта
или сопроводительная док-репа «без следов» (инвариант: docs/AGENTS не в истории
проектного гита). **Этап 0 фичи 04 закрыт этим ADR; отдельный ADR про трекер задач
НЕ заводится.**

**Отвергнуто:** БД для прозы (ревизия git-археологии — НЕ-цель фичи 04 §5); wasm/sql.js (lost-update);
devst.json как единственный маппинг (след в режиме «без следов»); реестр проектов машины сейчас; внешний трекер.

**Связанное:** [фича 04](../features/04-task-registry.md)
(протокол №1–19) · [ADR-015](adr-015-tauri-ui-stack.md) ·
[ADR-010](adr-010-detect-dont-block.md)/[ADR-013](adr-013-default-deny.md) · аудит дрейфа внешнего TTRPG-проекта (2026-09-11) · стандарт v1.6

## Контекст

⭐-вопрос из списка открытых вопросов (автор, 2026-09-10, сессия 6,
дословно): «в целом я ещё думаю насчёт улучшения нашего процесса хранения и работы с
данными devst». Оси: скорость парсинга на больших репах · целостность (рассинхрон копий) ·
удобство ведения (реестр freeze как таблица). Доказательство срочности —
аудит дрейфа внешнего TTRPG-проекта: 15 устаревших
фактов за неделю активной работы (медиана ≈ 8 дней), паттерны P1–P4. Дизайн ответа готов —
[фича 04](../features/04-task-registry.md)
(протокол №1–10); для старта этапов оставалось закрыть хранение: движок, доступ из UI,
порядок миграции, хостинг канона (раскрытие автора 2026-09-11), маппинг, WAL, параметры.

Боли автора (протокол №3 фичи 04, дословно): «Основная боль была в локах — щас есть UI,
будем в работе проверять» и «Руками к слову я вообще ничего не редачил пока что в доках —
я лентяй»: параллельная запись двух чатов и ручная правка md-таблиц.

Рамка прежнего забора (roadmap 2.2.1 / ADR-015): «markdown-канон — единственный источник
правды; кэши UI — только пересобираемые производные; смена формата частей канона или БД —
только через ADR». Этот ADR — такое изменение рамки: источник правды становится
двухсоставным (проза = md, реестры = БД).

## Опции

### Ось 1 — где живут структурированные реестры (freeze, сессии-индекс, задачи)

**A. Статус-кво: md-таблицы/списки в доках.**

- Плюсы: ничего не строить; читаемо без тулзы.
- Минусы: правка md-таблицы — боль (наблюдение автора в решении №3 фичи 04); P3 аудита —
  тройной учёт одного смысла (открытый вопрос + TODO + roadmap-чекбокс); файловые замены = локи при
  двух чатах; парсинг md-шапок задач.
- Вердикт: тупик-причина всей работы (аудит).

**B. БД как источник всего канона (включая прозу).**

- Плюсы: единый формат, быстрые запросы.
- Минусы: ревизия главной ценности md — переносимость, читаемость агентами без тулзы,
  git-археология (`git log -S`, диффы, мержи прозы); на ней построен метод аудита.
- Вердикт: отвергнуто (НЕ-цель фичи 04 §5).

**C. Гибрид: проза = md, реестры = SQLite (выбрана).** Движок CLI — `node:sqlite`:

- Плюсы: zero-deps (инвариант проекта — stdlib, не зависимость); Node на машине v24.14.1
  (требование ≥ 22.5 выполнено; в `engines` package.json сейчас `>=18` — поднять при
  этапе 1); транзакции, связи, индексы; возраст — вычисляемое свойство (таймеры фичи 04 §7).
- Минусы: binary-файл в гите — диффы нечитаемы (история реестра = снапшоты состояния;
  причинность живёт в `Closes T-NN` и log/); CLI-фичи реестра требуют Node ≥ 22.5
  (без тулзы md-фолбэк продолжает работать).

### Ось 2 — доступ UI к БД (этап 4, доска в Tauri-окне)

**A. wasm/sql.js в webview (in-memory + запись файла целиком через fs-плагин).**

- Плюсы: забор ADR-015 не тронут (ядро в webview, без IPC).
- Минусы: lost-update при двух писателях (CLI-чат параллельно с UI) — ровно та «боль в
  локах», ради которой переходят в БД; перезапись всего файла на каждую мутацию;
  транзакции не пересекают границу webview.

**B. Rust-сторона: rusqlite в Tauri-бэкенде + IPC-команды (выбрана).**

- Плюсы: нет lost-update — один писатель (процесс бэкенда), WAL и транзакции в одном
  процессе; файл БД не в памяти webview.
- Минусы: правит забор ADR-015 («ядро в webview без IPC») — появляется IPC-грань для
  реестра; Rust-сторона растёт.
- Смягчение: KernelAdapter (фича 03) гасит смену источника — экраны не знают, откуда
  данные; развилка сайдкара 2.3 и так ведёт к той же границе.

### Ось 3 — хостинг канона

Раскрытие автора (2026-09-11): «не во всех репах можно вести доки вместе с кодом — есть
репы с запретом оставлять следы (запрещено писать в репу вообще, включая .gitignore)».

**A. Только репа проекта (статус-кво стандарта §3).**

- Плюсы: доки версионируются с кодом; DoD/гейты/undocumented работают в одной репе.
- Минусы: неприменимо к репам «нельзя оставлять следы».

**B. Всегда внешняя док-репа.**

- Плюсы: один механизм на все случаи.
- Минусы: усложнение дефолта; для обычных реп соседство с кодом — живая ценность.

**C. Режимная модель (выбрана).**

- Дефолт — репа проекта.
- «Без следов» — сопроводительная док-репа: сосед `../name.docs/` (дефолт) или вложенно
  `project/my-docs/` (placement-флаг); своя гит-репа: docs/ (canon-проза) + registry.db
  (реестры гибрида) + config. **Инвариант режима: docs и AGENTS не видны в истории гита
  проекта нигде и не пушатся на его remote никогда.**
- Невидимость без правки проекта: `.git/info/exclude` (служебный, локальный, не
  коммитится) или глобальный `core.excludesFile` — НЕ `.gitignore` (правка проекта = след).
- Грабли вложенного размещения: явный `git add` ставит gitlink (лечится `rm --cached`,
  ловить доктору); `git clean` сносит вложенный `.git` только с `-ff`; бланк-копии
  рабочего дерева (архивы, docker context, артефакты) и сканеры заметнее внутри project/ —
  потому сосед дефолтен.
- Режимы AGENTS: (а) «без следов» (дефолт для помеченных реп) — AGENTS живёт в док-репе,
  точка входа агенту — скилл/маппинг; (б) «вне истории» (НЕ дефолт, opt-in) — AGENTS.md
  физически в корне «как обычно» + строка в .gitignore для типовых агентов, которые ищут
  AGENTS только в корне (строка .gitignore здесь — признанный след; спрятать и её можно
  info/exclude — per-project).
- Cloud-save: пуш док-репы в свою приватную remote (бэкап, мульти-машина) — дефолт
  выключен, включается per-project (решение №6 ниже); в проектный remote в режиме «без
  следов» не попадает никогда.
- Граница: если запрещены даже локальные заметки о коде — стандарт на репу не
  распространяется; обход политики не проектируем.

### Ось 4 — маппинг project root ↔ doc root

**A. devst.json в проекте (план roadmap 2.2).**

- Плюсы: конфиг рядом с проектом; естественно для дефолт-режима.
- Минусы: в режиме «без следов» файл в проекте — запрещённый след; годится только как
  вариант дефолт-режима, значит механизм не один.

**B. Реестр проектов машины (глобальный, вне реп).**

- Плюсы: единый механизм для всех режимов; готовит мета-доску.
- Минусы: глобальное состояние и новая сущность до второго потребителя (мета-доска —
  парковочная репа дальних идей; НЕ-цель фичи 04 §5).

**C. Конвенция + конфиг док-репы (выбрана):** дефолт — доки в корне проектной репы
(маппинг не нужен); док-репа сама несёт конфиг (путь проекта, placement). Реестр проектов
сейчас не делаем — вернуться при живой мета-доске.

### Ось 5 — параллельная запись

- Файловые замены md-реестров: локи и рассинхрон двух чатов — тупик для реестров (боль
  автора, протокол №3 фичи 04).
- Выбрано: БД-транзакции + один слой записи (apply-трансформеры фичи 03; после этапа 4
  CLI и UI пишут через один и тот же слой — UI через IPC Rust-стороны) +
  optimistic-concurrency на уровне записей. WAL-дисциплина при гит-отслеживании базы:
  чекпоинт перед коммитом (хук), `-wal`/`-shm` вне гита (.gitignore / excludes док-репы)
  — иначе коммит уходит без свежих транзакций.

## Решение

**Вариант — гибрид md+SQLite, UI через Rust-сторону, режимный хостинг.** Ответы автора
(батарея хранения, 2026-09-11, дословно — протокол фичи 04 §3, №11–19):

1. Гибрид: канон-проза остаётся md в git; реестры переезжают в SQLite по одному —
   freeze → сессии-индекс → задачи (порядок подтверждён, №13). Движок — `node:sqlite`,
   Node ≥ 22.5 (v24.14.1 — ок; engines поднять при этапе 1). Задачи рождаются сразу в БД.
   Реестр — источник правды реестровых данных, md — прозы; карта/панель — указатели,
   board читает реестр живьём.
2. UI (этап 4): реестр через Rust-сторону — rusqlite + Tauri-команды (№11); ADR-015
   дополняется «БД-гранью реестра» (append-only), проза остаётся через fs-плагин;
   экраны через KernelAdapter не меняются.
3. Хостинг: режимная модель (ось 3-C) — репа проекта по умолчанию; «без следов» —
   сопроводительная док-репа с инвариантом невидимости; режимы AGENTS; cloud-save —
   дефолт выключен, per-project (№16). Правки стандарта (принцип №3, §3) — v1.6.
4. Маппинг: конвенция «доки в корне» + конфиг в док-репе; реестр проектов машины не
   делаем (№12).
5. Параллельная запись: транзакции + один слой записи + optimistic-concurrency;
   WAL-дисциплина (ось 5).
6. Параметры трекера: TTL-дефолты 30/7/5/14 старт, калибровка по метрике медианного
   возраста дрейфа (база ~8 дней); severity дефолта warn, strict — осознанный opt-in
   (№14); имя команды `devst board`, алиасы show-tasks-board / show-tasks-board-short
   (№15); иных болей хранения нет (№18).
7. Миграция devst на себя (этап 6 фичи 04) — отдельной сессией после этапов 1–2 (нужны
   `task new/close` и `board`: миграция делается тулзой, не руками) (№17).
8. **Видимая пометка развилки:** отдельный ADR про трекер задач НЕ заводится — этап 0
   фичи 04 закрывается этим ADR целиком: развилки хранения/хостинга/миграции — здесь, в
   Опциях; «почему такой трекер» уже зафиксировано протоколом №1–10 в фиче 04 (capture —
   единственное место учёта, иначе дублирование = P3 аудита). Ответ автора (№19,
   дословно): «Я до сих пор не понимаю вопрос. Сделай свой Recommended, но явно пометь
   в доке где-то В ВИДИМОМ МЕСТЕ!!! Эту развилку». Пометка продублирована в трёх видимых
   местах: шапка этого ADR (Суть) · фича 04 §4 (строка этапа 0) · log-запись сессии 16.
   Самостоятельный ADR о трекере — только НОВЫЙ ADR по факту будущей развилки.

## Обоснование

- Гибрид сохраняет ценность обеих форм: git-археология и читаемость прозы + транзакции,
  связи и таймеры реестров (ось 1-C против тупика A и ревизии B).
- Критерий оси 2 — «боль в локах»: wasm-вариант воспроизводит её на уровне файла,
  Rust-сторона устраняет одним писателем; цена (IPC-грань) застрахована KernelAdapter'ом.
- Инвариант «без следов» жёстче любых удобств: невидимость в истории и пуше проектного
  гита не компрометируется даже строкой .gitignore без явного opt-in автора.
- Zero-deps сохранён: `node:sqlite` — stdlib Node, не зависимость.

## Последствия

**Позитивные:**

- Реестры получают транзакции/связи/индексы; параллельная запись двух чатов решена;
  md-таблицы freeze и ручной тройной учёт уходят по мере миграции (freeze → сессии → задачи).
- Репы «нельзя оставлять следы» покрываются стандартом без компромисса инварианта.
- Вопросы/задачи с таймерами и связями ловят дрейф поимённо (фича 04 §7–9).

**Негативные / риски:**

- registry.db в гите — бинарные снапшоты; `git log -S` по реестру не работает —
  причинность только через `Closes T-NN` и log/ (осознанно принять).
- Node ≥ 22.5 для CLI-фич реестра; проекты на старом Node остаются на md-фолбэке.
- ADR-015 дополнен IPC-гранью: проза и реестр идут разными путями записи — правило
  «мутации канона через apply-трансформеры» обязано покрывать оба пути.
- Док-репа — второй гит-клон: синхронизация веток/remote на авторе; вложенный режим —
  грабли gitlink/clean-ff, доктор обязан их ловить.
- WAL-дисциплина требует хук-чекпоинта: без него коммит уносит базу без свежих
  транзакций (тихая потеря хвоста).
