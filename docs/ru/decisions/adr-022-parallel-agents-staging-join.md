# ADR-022: Параллельные агенты: staging-реестры задач и join

> Русский · [English](../../decisions/adr-022-parallel-agents-staging-join.md)

> **Статус:** Принято · **Дата:** 2026-09-25

**Суть:** параллельные агенты пишут задачи в staging-журналы
`docs/registry-inbox/<сессия>--<агент>.db` (git-tracked) и заливаются в канон
идемпотентным join'ом; номер задачи аллоцируется из канона при `task new`;
staging — только задачи. Канон `registry.db` не меняется — дополнение оси 5
ADR-017 (гит-уровень параллельности, который она не закрывала).

**Отвергнуто:** очередь коммитов (авторская боль дословно); локальные ID с
перенумерацией при join (ломает «Closes T-NN»/touch/гейт); md/ndjson-журнал;
SQLite-лок как полное решение.

**Связанное:** [ADR-017](adr-017-hybrid-storage-md-sqlite.md) (ось 5) ·
[фича 04](../features/04-task-registry.md) (Closes-гейт §7) ·
Zen-Shell (консервированный дизайн борда из парковочной репы дальних идей) ·
внутренняя методология dev-standard v1.6.

## Контекст

ADR-017 (ось 5) решил одновременную запись двух чатов в **один файл** реестра:
транзакции + один слой записи + optimistic-concurrency. Гит-уровень остался дырой:

- **одна рабочая копия** — правки обоих агентов перемешиваются в одном `registry.db`
  и одном working tree; коммитить нельзя, пока оба не закончили;
- **worktree** — у каждого агента своя копия канона; мерж веток, обе тронувших
  бинарный файл, невозможен в принципе.

Проявление (автор, 2026-09-25, дословно): «нельзя закоммитить пока оба из них не
закончат работу, иначе потом не разобрать "что и от кого"».

Предложение автора (2026-09-25, дословно): «решение вижу временным под задачу
небольшим db (их может быть много, по сути временные файлы) — который потом мы
join в основной регистр задач. Там как раз из ZenShell может что-то пригодится?»

Zen-Shell (консервированный дизайн борда из парковочной репы дальних идей):
прямого join-механизма нет (карточки — md-секции, не БД); переиспользуются два
приёма — «агент пишет только в inbox» (board/inbox.md) и «каждое перемещение =
коммит» (гит как бесплатная атрибуция).

Ограничение совместимости: `T-NN` сквозные и на них завязано всё (фича 04 §7) —
`Closes T-NN` в коммитах кода, touch собирается grep'ом истории
(`collectTouchForTask`), гейт сессии сверяет Closes со статусами реестра.

## Опции

### Ось 1 — как развести параллельных агентов

**A. Очередь коммитов (коммитим по завершении обоих).** Плюсы: ноль кода.
Минусы: атрибуция теряется (боль автора дословно); параллельность фиктивна.
Вердикт: тупик.

**B. Локальные ID в staging + перенумерация при join.** Плюсы: полностью офлайн,
канон не нужен до join'а. Минусы: агент не знает финальный ID в момент коммита
кода → «Closes T-NN» в сообщениях, touch по grep'у истории и гейт сессии надо
переучивать на staging-журналы — дорогая переделка работающей цепочки.
Вердикт: фолбэк для мульти-машины (вне текущего скоупа), не дефолт.

**C. Staging-журналы + join (выбрана).** Каждый агент пишет только в свой файл;
канон мутирует одним писателем — операцией join. Плюсы: атрибуцию даёт гит
(один файл = одна сессия одного агента, коммит того же агента); бинарных
конфликтов нет (файлы разные); «Closes»-цепочка не меняется (см. ось 3).
Минусы: новый слой (inbox/join) в `registry-run`; нужен отчёт конфликтов join'а.

### Ось 2 — формат staging

**A. Копия схемы (те же таблицы tasks).** Плюсы: переиспользование SQL.
Минусы: join мержит снапшоты строк — по-полевый конфликт-резолв, потеря истории
операций.

**B. Append-only журнал операций (выбрана).** Staging хранит мутации
(`task new/set/link/status`), join = детерминированный replay, идемпотентный по
(агент, сессия, seq). Плюсы: повторный join безопасен; история операций = досье
сессии. Минусы: схема журнала — новая сущность (рядом с задачами фичи 04).

**C. md/ndjson-журнал.** Плюсы: текст в диффах. Минусы: второй формат записи
поверх схемы + валидация replay руками; staging-БД тем же `node:sqlite`
переиспользует ядро `registry.ts` — меньше кода. Вердикт: отвергнуто.

### Ось 3 — нумерация задач

**A. Аллокация номера из канон-БД в момент `task new` (выбрана).** Короткая
атомарная транзакция; на одной машине все агенты делят один файл канона —
SQLite-лок это держит. Join доливает контент по уже готовому ID: «Closes T-NN»,
touch и гейт работают как сейчас. Минусы: staging-агент должен знать путь канона
(worktree ≠ канон — см. Последствия).

**B. Номер при join (локальные ID)** — см. ось 1-B; отвергнуто как дефолт.

## Решение

**Вариант — staging-журналы + идемпотентный join; канон не меняется.** Ответы
автора (2026-09-25, дословно — батарея по трём развилкам):

1. Схема «staging + join» принята (№1: «1 - да, норм»): staging —
   `docs/registry-inbox/<сессия>--<агент>.db`, git-tracked; WAL-дисциплина как в
   ADR-017 ось 5 (чекпоинт перед коммитом, `-wal`/`-shm` вне гита). Join —
   явная команда, идемпотентный replay; конфликт «обе стороны правили одну
   задачу» — резолв по `updated_at` (latest-wins) + предупреждение в `board`,
   не молчаливый апсерт. Присоединённый файл удаляется коммитом join'а.
2. Номер задачи аллоцируется из канон-БД в момент `task new` (№1: «1 - да,
   норм») — `Closes T-NN`/touch/гейт сохраняются без переделки.
3. Формат staging — append-only журнал операций, не копия схемы (№2: «2 - да,
   хорошо»).
4. В staging — только задачи; freeze (канон `freeze_canon='db'`, редкие
   операции) — напрямую в канон (№3: «3 - согласен, только для задач»).
5. Из Zen-Shell переиспользуются приёмы «агент пишет только в inbox» и «каждое
   перемещение = коммит»; механизм join там отсутствует — не источник.

Флоу: код — по веткам/worktree, реестр — через свои inbox-файлы, канон — по
очереди через join (порядок с мержем не важен). До join'а `board` показывает
«висит в inbox» — видимость чужой параллельной работы, то есть «разобрать что и
от кого» ещё до коммита.

## Обоснование

- Канон и правила фичи 04 не меняются: это дополнение оси 5 ADR-017, не ревизия;
  смена формата/канона — только ADR (рамка roadmap 2.2.1) — соблюдено.
- Атрибуция («что и от кого») решается гитом бесплатно: один staging-файл — одна
  сессия одного агента; join-коммит ссылается на сессию.
- Цепочка `Closes T-NN` → touch → гейт сессии сохранена без переделки (ось 3-A).
- Zero-deps сохранён: staging — тот же `node:sqlite`, stdlib.

## Последствия

**Позитивные:**

- Два агента работают параллельно без блокировки коммитов (код — ветки, реестр —
  inbox-файлы, канон — очередь join'ов).
- Незалитая работа чужой сессии видна на доске до коммита.
- История операций сессии — в её staging-файле (досье для разбора инцидентов).

**Негативные / риски:**

- Аллокация ID требует доступа к канон-БД из worktree: in-repo — канон в основной
  рабочей копии (нужен механизм «канонический путь реестра»); для внешнего
  док-репа канон один — ок. Мульти-машина вне скоупа: там фолбэк — ось 1-B
  (локальные ID + перенумерация) — отдельная развилка при появлении случая.
- Новый слой inbox/join в `registry-run` (схема журнала, replay, отчёт
  конфликтов) — реализация отдельной задачей; до неё агенты работают по-старому.
- Touch задачи наполняется после мержа ветки агента (Closes-коммиты уходят в
  его ветку) — между join'ом и мержем гейт может показывать «декларация не
  подтверждена»; это warn, не блокер.
