# ADR-014: Сверка требований ТЗ ↔ бек ↔ фронт (docs/requirements.md)

> Русский · [English](../../decisions/adr-014-req-reconcile.md)

> **Статус:** принято · **Дата:** 2026-09-08

**Суть:** профильная дока `docs/requirements.md` — строки R-NN «требование дословно / факт бека / вердикт-кто прав / дельта / действие / дата»; ритуал `/req-check`; напоминание в SessionStart при незакрытых > 3. dev-standard → v1.4.

**Отвергнуто:** таблицы внутри отдельных фич (нет сводного вида и сквозных ID); проверка фактов только руками автора (агент проверяет сам — источник объявлен в шапке доки); удаление закрытых строк (потеряли бы базу знаний «кто был прав»).

**Связанное:** [ADR-011](adr-011-ui-freeze.md) (паттерн профильных док) · [ADR-005](adr-005-env-in-l0.md) (источники бека)

## Контекст

Запрос автора: «ТЗ может расходиться и с тем, что по факту нужно сделать, и с тем, что вообще есть на беке — проверить всех и записать "кто прав и насколько"». Все четыре решения — рекомендованные варианты автора.

## Решение

1. Таксономия вердиктов: сходится / ТЗ прав / бек прав / оба врут / ждёт ответа + колонка «Дельта» (в чём именно расхождение).
2. Механика: парсер `req.ts` (строка считается незакрытой, когда факт пуст или «ждёт ответа»), линт шапки доки, `reqOpen` в `check --json` → строка в SessionStart при > 3 незакрытых.
3. Ритуал `/req-check`: агент проверяет по источнику, объявленному в шапке доки (OpenAPI / репозиторий бекенда в read-only / живой API); факт — дословная точность; абсолютное правило подтверждения действует для вердиктов «оба врут» и для перезаписи утверждённых вердиктов.
4. Имя шаблона — REQ-RECONCILE.md (REQUIREMENTS.md уже занят T3-трассировкой docs-hub).

## Последствия

Опциональность by design (нет файла — молчим); эскалации: архитектура → ADR, вопросы → open-questions, строка с пометкой «ждёт ответа».
